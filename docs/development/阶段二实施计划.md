## 运行设计

- API 与生成过程分离，创建运行的事务提交后再执行模型。模型调用期间不持有数据库事务。
- 同一对话串行生成；不同对话可独立执行，各使用独立 AsyncSession。
- 创建运行时锁定对话行，按 next_message_sequence 分配用户和助手消息序号，在一个事务中写入三者并推进计数器。
- 相同幂等键和相同请求返回已有运行；相同键但内容不同返回 409。数据库唯一约束是最后防线。
- 一次运行对应一个助手消息；流式文本批量保存到这条消息，取消或失败保留已保存文本并标记 interrupted。
- 先查询业务消息重建上下文，后续后台任务阶段再接入持久化 LangGraph 检查点；业务表不充当检查点。
- 本阶段本机单进程执行。队列、Worker 和跨进程恢复在阶段五实现；服务重启后将遗留未结束运行收敛为失败，并保留部分回答。已在首次问答访问时实现状态收敛。
- SDK 通过统一适配层接入。测试使用可控替身，真实接入采用 DeepSeek 官方 API。API Key 仅在本地 .env 填写，不通过聊天传递、不进入日志。

## 已实现接口契约

|接口|用途|
|---|---|
|POST /api/conversations|创建对话，校验标题|
|GET /api/conversations|按更新时间分页列出对话|
|GET /api/conversations/{id}/messages|按 sequence 查询历史，分页|
|POST /api/conversations/{id}/runs|提交问题与 idempotency_key，返回运行及消息标识|
|GET /api/runs/{id}|查询运行的权威状态|
|GET /api/runs/{id}/events|SSE 订阅，支持恢复已持久化内容|
|POST /api/runs/{id}/cancel|幂等请求停止，最终状态通过查询或 SSE 确认|

SSE 实际采用 snapshot、completed、failed、cancelled 完整快照事件；不提供 delta 或事件游标回放。精确契约、恢复、限制见 [阶段二架构与接口](阶段二架构与接口.md)。

## 技术取舍

- 采用三表分离：相比将状态塞进消息，能保留失败和重试记录，方便后续观测；代价是需要明确事务边界。
- 采用 PostgreSQL 部分唯一索引：并发限制在数据库内成立；代价是迁移和验证需要真实 PostgreSQL，不使用 SQLite 代替。
- 采用业务消息重建上下文：便于先验证问答持久化；长对话裁剪、检查点与任务恢复后续按阶段完善。
