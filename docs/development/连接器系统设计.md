## 一、WorkBuddy 连接器架构分析

WorkBuddy 的"连接器"本质是**三种集成模式的统一抽象**：

| 模式 | 示例 | 技术原理 |
|---|---|---|
| **CLI 连接器** | 腾讯会议、钉钉、企业微信 | 封装命令行工具，`subprocess` 调用 |
| **MCP 连接器** | 通达信、天眼查 | MCP 协议（JSON-RPC），自动发现工具 |
| **API 连接器** | QQ邮箱、腾讯文档 | 直接调 REST API |

核心设计特征：
1. **统一工具抽象**：不管底层是 CLI/MCP/API，最终都暴露为"工具"给 Agent
2. **连接器市场**：卡片式展示，用户可浏览、启用、配置
3. **自定义连接器**：用户可自定义新连接器
4. **状态管理**：每个连接器有连接状态（已连接/未配置/错误）

## 二、MCP 协议简介

MCP (Model Context Protocol) 是 Anthropic 的标准协议（类似 USB 接口）：
- **MCP Server**：暴露 tools / resources / prompts（定义 `name` + `description` + `inputSchema`）
- **MCP Client**：`list_tools()` 发现工具，`call_tool()` 调用工具
- **传输**：stdio（子进程）、SSE/HTTP（远程服务）
- **Python SDK**：`mcp` 包（需安装）

**分层原则**：连接器层只做"外部工具 → ToolSpec"的翻译；身份、审批、审计、配额、装配全部交给现有能力层。

## 四、核心接口定义

新目录 `backend/app/connectors/`：

```python
# base.py
ConnectorKind = Literal["cli", "mcp", "api"]
ConnectorStatus = Literal["disabled", "connected", "degraded", "error"]

class Connector(Protocol):
    key: str                    # 稳定标识
    kind: ConnectorKind

    def config_fields(self) -> tuple[ConfigField, ...]:
        """声明配置项（含是否密钥），前端渲染 + 校验。"""

    async def connect(self) -> ConnectorStatusInfo:
        """建立会话/健康检查。"""

    async def check_health(self) -> ConnectorStatusInfo:
        """检查当前实例的连接与认证状态。"""

    async def list_tools(self) -> list[ConnectorToolDef]:
        """发现工具：MCP 走 list_tools()；CLI/API 为声明式定义。"""

    def tool_specs(self, defs, policy) -> list[ToolSpec]:
        """把工具定义映射为 ToolSpec。"""

    async def call(self, name: str, arguments: dict) -> object:
        """执行一次外部调用。"""

    async def aclose(self) -> None:
        """释放资源。"""
```

### 腾讯会议认证与失败处理（2026-11-17 修复）

- 微信绑定只建立消息渠道；腾讯会议查询还需要后端运行账号完成 `tmeet` OAuth 登录。
- CLI 可执行文件优先从项目 `tools/node_modules/.bin` 解析，再查系统 PATH。
- 腾讯会议健康检查依次执行 `--version` 和 `auth status`。`auth status` 未登录时仍可能退出码为零，必须识别文本状态；未登录显示“请完成账号授权”，不再展示连接正常。其他 CLI 仍使用原有版本检查。
- `auth_status` 工具返回结构化 `logged_in` 状态；不把账号标识、Token 状态文本回传模型，也不对 CLI 的文本状态强行解析 JSON。
- CLI 命令模板里的可选 `--option {value}` 在值为 `None` 时整组省略，保留 CLI 自带的默认时间窗口；显式传入的查询条件和默认分页参数保持不变。
- 工具执行层只公开白名单错误码和固定中文提示，不向模型或审计透传原始 stderr：

| 底层分类 | 工具错误码 | 处理建议 |
|---|---|---|
| `not_logged_in` | `CONNECTOR_NOT_LOGGED_IN` | 在后端运行账号下完成账号授权后重试 |
| `permission_denied` | `CONNECTOR_PERMISSION_DENIED` | 检查账号授权范围 |
| `timeout` | `TOOL_TIMEOUT` | 稍后重试 |
| `invalid_output` | `CONNECTOR_INVALID_OUTPUT` | 检查 CLI 版本和返回格式 |
| `command_failed` | `CONNECTOR_COMMAND_FAILED` | 检查连接器状态和配置 |
| 未知异常或分类 | `TOOL_EXECUTION_FAILED` | 保持通用错误，避免泄露内部信息 |

### 持续监控与授权提醒（2026-11-18）

后台在启动时检查已启用连接器，随后每 60 秒探测一次。`ConnectorRegistry` 复用现有实例执行健康检查，每个连接器独立超时。同一连接器的并发检查共享结果，配置更新与检查按连接器串行执行。真实工具调用成功或失败后也会立即更新状态。实例更新前发起的迟到结果会被忽略。

页面通过共享 Pinia Store 每 15 秒读取状态，隐藏标签页暂停轮询，重新显示时刷新。登录用户和工作空间切换后清理旧状态并忽略旧响应。全局持续提醒列出需要授权或配置的已启用连接器。管理员可跳转到对应配置抽屉，普通成员看到联系管理员提示。连接器停用后停止探测并清除待处理操作。

认证状态与连接状态独立记录。网络或 DNS 失败将认证标记为待确认，保留上次成功时间。只有明确的未登录、缺失密钥或 401 才提示授权或配置。

| 字段 | 含义 |
|---|---|
| `status` | 原有 `disabled/connected/degraded/error` 连接状态 |
| `auth_status` | `unknown/authorized/required/not_required` 认证结果 |
| `auth_action` | 服务端推导的 `authorize/configure/retry` 操作，正常或停用时为空 |
| `last_error_code` | 固定公开错误分类 |
| `last_checked_at` | 最近检查或工具调用反馈时间 |
| `last_success_at` | 最近成功检查或工具调用时间，失败时保留 |

迁移 `0018` 为 `connectors` 增加 `auth_status`、`last_error_code`、`last_success_at`，复用原有检查时间和错误信息列。旧数据的认证状态默认为 `unknown`，启动检查确认后更新。迁移完成后的就绪版本为 `18`。

#### 各类连接器的检查方式

- 腾讯会议 CLI 执行版本检查和 `auth status`，识别未登录的零退出码及刷新期间的网络错误。已确认授权时点击授权直接返回成功。
- API 连接器先检查必需密钥，再使用可选 `health_path` 发起 GET 请求验证。路径必须是当前 `base_url` 下以 `/` 开头的相对路径。健康请求使用配置的认证头和前缀，管理员应选择服务提供的只读、无计费探测接口。
- 内置 Tavily 使用官方地址时默认以 `GET /usage` 验证密钥，适用于既有安装和新安装。检查不执行搜索，配置了健康路径时使用指定路径。其他 API 未配置健康路径时显示待确认，实际业务调用成功可确认连接与认证。401 提示更新凭证，403 提示检查权限。配置页保存的密钥从 `integration_configs` 注入后端实例，内置 Tavily 兼容原有 `EA_TAVILY_API_KEY` 配置。参见 [Tavily Usage API](https://docs.tavily.com/documentation/api-reference/endpoint/usage)。
- 连接器页面按标识合并内置目录和已安装状态，在同一列表支持名称、描述和标识搜索。管理员点击未连接卡片的「＋」安装并启用、重新启用或进入授权配置。已连接卡片显示健康状态并提供管理入口，检查时间、工具列表、配置与启停集中在详情抽屉。
- MCP 通过现有会话发送 ping，并对 SDK 包装的 HTTP 401 进行分类。单纯 ping 成功时，认证状态仍为未知，业务调用成功后确认认证。

#### 授权进程生命周期

`POST /api/admin/connectors/{key}/auth` 对腾讯会议创建或复用一个后台登录流程。取得官方授权链接后及时返回，首次最多等待 8 秒，后台保留最多 5 分钟等待扫码。进行中的并发请求共享流程。页面提供授权链接，每 2 秒串行读取授权进度，结束后执行健康复查并刷新全局提醒。

授权 URL 只接受 `https://meeting.tencent.com/marketplace/tencentmeeting-cli-auth.html` 和非空授权码，原始 CLI 输出不会回传客户端。URL 出现分段输出时，等待完整链接再公开。配置更改、停用和服务关闭会回收该流程拥有的进程树及输出线程。服务重启后，前端通过状态复查确认是否已经授权。

认证与授权接口保持管理员权限，授权进度响应禁止缓存。前端健康检查请求允许 65 秒，授权启动允许 90 秒，以覆盖后端可配置检查超时及获取链接的等待时间。

| 配置项 | 默认值 | 范围 |
|---|---|---|
| `EA_CONNECTOR_MONITOR_ENABLED` | `true` | 是否启用后台定时检查 |
| `EA_CONNECTOR_MONITOR_INTERVAL_SECONDS` | `60` | 1 至 3600 秒 |
| `EA_CONNECTOR_CHECK_TIMEOUT_SECONDS` | `15` | 大于 0 且不超过 60 秒 |

部署或更新时先在 `backend/` 执行 `uv run alembic upgrade head`，随后启动后端。数据库中的检查结果仅含状态和固定提示，账号凭证仍由原有密钥存储管理。

本次真实配置验证中，腾讯会议检查结果为 `connected/authorized`，启动监控后检查时间持续推进。Tavily 已配置密钥但缺少只读健康路径，结果为 `degraded/unknown`。自动化测试使用受控进程验证授权等待、到期、关闭与进程树清理，HTTP 集成测试验证管理员权限及状态契约，真实数据库测试验证检查持久化和并发停用。新后台授权流程的真实扫码端到端验收仍待进行，现有账号保持已授权。

### 免费基金行情连接器（2026-11-18）

- 在「连接器」页找到 **基金行情**，点击卡片上的「＋」安装并启用。目录标识为 `fund_market`，沿用 API 分类、安装、启停、健康检查和工具注册。它在后端进程中调用 [AKShare](https://akshare.akfamily.xyz/data/fund/fund_public.html)，无需另起 REST 服务、配置 API 地址或申请 Key。
- 后端通过 `uv sync` 安装锁定的 AKShare 依赖。启用时对一只公开基金的净值执行健康检查，标记为无需授权。短期缓存合并重复查询，三个工具均为只读，内置助手可直接调用。无需数据库迁移。

|---|---|---|
|`fund_market__etf_quote`|沪深 ETF 六位代码，如 `510300`|最近一分钟成交行情和最近最多 15 个分钟点。`as_of` 是行情时间。涨跌幅以数据中上一行情日最后一笔分钟价为参考，输出参考时间。|

### 个人养基宝持仓连接器

- 后端主机将 `fundpeek` 放入项目的 `.local/bin`，Windows 使用 `fundpeek.exe`。部署时也可以通过 `EA_YANGJIBAO_CLI_PATH` 指定可执行文件的绝对路径。
- 管理员在统一连接器列表点击「养基宝持仓」卡片的「＋」，按抽屉提示点击「扫码连接」，使用手机微信扫一扫并确认。页面内展示二维码，每 2 秒串行检查，过期可以重新获取。绑定账号可以重新扫码。
- `POST /api/admin/connectors/yangjibao/auth` 获取一次性二维码，`POST /api/admin/connectors/yangjibao/auth/status` 查询上游并在确认后保存授权。两个接口要求 Cookie、空间管理员、Origin 和 CSRF。临时会话仅当前进程持有，按发起人和工作空间隔离。后端通过 HTTPS 联系养基宝，前端只把上游的微信扫码内容编码成图片，不把它作为浏览器访问地址。
- 首次确认后，后端在连接器配置中记录当前工作台账号，并把凭据存到服务账号的 `~/.enterprise-agent/yangjibao/<user.id>`。可通过 `EA_YANGJIBAO_CONFIG_DIR` 覆盖根目录。凭据和持仓缓存目录应仅允许后端运行账号访问。已配置 `EA_YANGJIBAO_OWNER_USER_ID` 和独立授权目录的部署可以继续读取原凭据。
- 健康检查通过 `fundpeek status` 确认本机凭据，读取持仓执行 `sync yjb` 和 `json`，同步失败时停止读取快照。扫码归属与凭据路径不接受前端配置提交。
- 「连接器 → 养基宝持仓 → 查看持仓」按需同步并显示持仓金额、盘中估算涨跌幅、最新披露净值涨跌幅及各自的行情时间。上游标记缺失的数值显示「暂无」。`GET /api/connectors/yangjibao/holdings` 校验登录会话、当前空间成员关系和绑定账号，响应禁止缓存。点击「刷新持仓」重新同步。
- 展开基金详情可查看持有份额、持仓成本、每份成本、盘中估算市值、按最新净值计算的市值和参考单日收益。这些字段沿用同一次 CLI 同步结果。参考单日收益优先采用估值口径，在 CLI 缺少估值时可按最近披露净值计算。
- `yangjibao__list_holdings` 提供基金代码、名称、数量和同步时间。`yangjibao__get_portfolio` 用于问答查询持仓明细，返回与页面相同的持仓金额、份额、成本、市值、涨跌幅、参考单日收益和行情时间，缺失数据为 `null`。
- 两个工具均为只读，无需传入账号，默认装配给绑定账号，也可配置给该账号的自定义 Agent。恢复运行快照及执行前重新核验账号。问答调用明细工具时，结果作为本次工具输出提供给模型，工具审计仅保存基金数量。

连接器支持单个工作台账号，沿用安装和启停机制，无需数据库迁移。

验收覆盖真实上游取码与待扫码状态、页面内渲染与过期重试。数据库集成测试使用模拟的上游确认和 CLI 输出，验证绑定持久化、工具可见性以及同空间管理员无法读取或提交他人的扫码会话。已有 CLI 验收曾实际同步并解析 4 只基金。

## 七、前端设计

- **`ConnectorsView.vue`**（`/capabilities?tab=connectors`）：能力中心的「插件」标签。成员可搜索目录、筛选「我的插件」及管理本人已绑定的账号。`/plugins` 与 `/connectors` 均重定向到该标签，并保留 `connector` 深链接。
- **`AdminPluginsView.vue`**（`/admin/plugins`）：能力中心的「插件管理」标签，仅当前活动空间的管理员可访问。管理员可筛选启停状态、查看授权方式和详情。首次启用时复用现有安装与启用接口，已安装的插件可直接启停。安装与启停使用部署共享的连接器记录，影响全部工作空间，空间级工具策略继续按现有规则生效。
- 工具标签复用现有工具目录；`GET /api/tools` 及单项接口附带可空 `connector_key`，用于标识来源及双向跳转。`/capabilities?tab=tools&source=<key>` 只筛选当前账号可见的工具，不改变工具装配、可见性、空间启停或审批策略。
  - 成员卡片展示插件开放状态、个人绑定状态和可查看的工具。管理员共享授权与配置继续使用配置抽屉。
  - 成员端与后台采用同一套浅绿导航、面板、边线、操作反馈和窄屏布局。全站样式由 `frontend/src/styles/variables.scss` 和 `main.scss` 维护。

## 十、关键优势

- **零侵入现有架构**：连接器只做"翻译"，能力层完全复用
- **三种模式统一**：CLI / MCP / API 都产出 ToolSpec
- **热更新**：配置修改即生效，无需重启
- **扩展性**：新增连接器 = 实现 Connector 协议 + 注册
- **MCP 标准兼容**：可接入任何 MCP Server（通达信、天眼查等）

### QQ 邮箱、ima 和腾讯新闻个人连接器

管理员在「能力中心 → 插件管理」启用应用。QQ 邮箱开放后，成员进入「能力中心 → 插件」，用「添加」直接打开「我的账号」，填写 QQ 邮箱地址和 IMAP 授权码。绑定后「去问答」打开默认助手的新对话，示例问题只预填到空白草稿，成员自行发送。页面的「凭证已保存」表示绑定记录已写入，QQ 邮箱授权在实际查询时验证。

管理员的插件详情展示插件配置和工具。个人账号表单在「插件」标签按当前成员与工作空间展示。停用插件会暂停工具调用并保留原绑定，成员仍可从已绑定的卡片解除绑定。

ima 的「我的账号」支持主动检查本人绑定。知识库与笔记分别做限时只读检查，零命中属于成功，失败项可复制诊断编号。检查结果和耗时可在[系统日志](系统日志管理设计.md)中查询。

#### 部署和绑定接口

在 backend 目录运行 `uv run alembic upgrade head` 应用迁移 `0020`。为所有后端实例配置相同、长期保存的 `EA_CONNECTOR_CREDENTIAL_KEY`，值取自 `cryptography.fernet.Fernet.generate_key()`。把密钥保存在部署密钥配置或本机忽略跟踪的 `.env` 中，并随恢复方案备份。更换部署密钥会使旧绑定无法解密，需要重新绑定。

| 端点 | 返回或效果 |
|---|---|
| `GET /api/connectors/{key}` | `personal_account` 包含本人的绑定状态、字段定义和官方授权入口。 |
| `PUT /api/connectors/{key}/my-account` | 接收 `{"credentials": {...}}`，新增或整体替换自己的凭证。 |
| `DELETE /api/connectors/{key}/my-account` | 删除本人凭证，停用后仍可解绑。 |

登录会话和已验证的工作空间决定凭证归属。数据库以空间、用户、连接器为复合主键，保存 Fernet 密文。模型仅看到工具参数，每次调用按运行归属重新获取绑定。解绑或停用后，即使旧 Run 已装配相应工具，也无法发起新的外部查询。工具审计只保存动作名，问答中的回答按现有私有会话规则保存。
