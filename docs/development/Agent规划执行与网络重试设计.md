# Agent 规划、执行与网络重试设计

> 2026-11-05 产品方向已调整为对话内规划与子 Agent。本文独立 Task 的设计/接口作为历史与后端兼容参考；不再提供独立前端入口。当前能力和恢复边界以 [对话内规划与子 Agent](对话内规划与子Agent实施.md) 为准。

日期：2026-11-04。本文保留原始设计目标。已交付的本地实现、配置和差异以 [规划执行实现与接口](规划执行实现与接口.md) 为准；验收见 [规划执行验收记录](规划执行验收记录.md)。SDK 内部节点检查点、自由多轮任务 ReAct 与独立 Worker 仍属于后续范围。

## 1. 设计时的基础与目标（历史基线）

设计时核对的基线代码：Deep Agents 支持受控的模型—工具循环；只开放 get_my_run_stats；图 recursion_limit=10，工具实际执行默认最多 4 次。供应商 SDK max_retries=0；ChatRuntime 对一次问答设置总超时，异常通常直接终止，重启将旧运行收敛为失败。尚无持久化计划、步骤执行器、退避重试或检查点恢复。

目标是让用户看见“准备做什么、现在做到哪一步、为什么在等待、失败后从哪里继续”。以下均为拟议能力，不代表已经交付。普通问答仍保持轻量，不自动变成业务任务；不增加预算填写。

## 2. 方案选择

|方案|优点|代价|选择|
|---|---|---|---|
|完全交给自由 ReAct 循环|接入快、模型灵活|难保证进度、边界、可恢复性|只保留在单个步骤内部|
|计划后逐步执行，步骤内有限 ReAct|计划、进度、重试与审计可控|需建立步骤和尝试模型|首版推荐|
|立即加入队列、多个 Worker 与并行子 Agent|适合长任务与规模化|当前本地项目增加运维和并发复杂度|之后扩展|

采用“Planner → 校验与用户确认 → Executor → 结果校验 → 汇总”。业务状态由服务端状态机决定，LLM 负责提出计划、选择允许的工具和生成内容，不能自行宣告外部操作成功。

首版使用现有 FastAPI + PostgreSQL + 本地异步调度器，不要求 Docker、Redis 或 Celery，也不依赖 MCP。保持只有一个任务执行进程；浏览器关闭后服务进程仍可执行，但电脑或后端停止期间不会运行。

## 3. 产品流程与规划

用户在问答中显式点击“按计划执行”或“转为任务”，才能创建任务。提交目标后生成草案，用户可以修改和确认，确认前不执行工具。普通问题仍沿用当前问答入口。

示例：“分析我最近 7 天的运行情况，并给出改进建议。”

1. 查询本人当前空间最近 7 天运行分布。
2. 根据已取得的统计分析成功、失败和取消情况。
3. 汇总结论与建议，标明统计时间和数据范围。

只有现有工具能支持的步骤才能执行。当前有运行统计和知识库检索工具，但没有外网搜索和业务写入工具，因此计划不能把“修改客户记录”等步骤显示为可执行；知识库检索需在配置 RAGFlow 后使用。

每个步骤包含：step_id、标题、类型、depends_on、所需工具、参数/输入绑定、输出契约、完成条件和重试策略标识。模型不能提交用户身份、空间身份、任意 SQL、命令或自定义重试次数。

服务端校验：工具白名单、参数结构、依赖存在、无循环依赖、步骤数上限、输入输出引用、权限与能力是否具备。用户确认绑定完整 plan_revision 和内容摘要；修改后生成新版本并重新确认，不能沿用旧确认。

首版默认串行执行。数据结构保留依赖关系，为后续 DAG 并行做准备，但本次不把有依赖的步骤同时执行。

## 4. 执行结构与边界

~~~mermaid
flowchart TD
    A[用户提交目标] --> B[Planner 生成计划草案]
    B --> C[服务端校验能力、依赖与输入]
    C --> D[用户确认计划版本]
    D --> E[选择依赖已完成的步骤]
    E --> F[执行前复核权限与取消状态]
    F --> G[步骤内部有限 ReAct 循环]
    G --> H[校验输出和真实执行证据]
    H --> I[事务提交步骤结果与事件]
    I --> J{全部完成?}
    J -->|否| E
    J -->|是| K[汇总并标记任务完成]
    G --> L[异常分类]
    L -->|暂时性且允许重试| M[保存 retry_wait 和 next_retry_at]
    M --> F
    L -->|永久失败或次数耗尽| N[失败并保留已完成结果]
~~~

模块职责：

- PlannerService：从目标和当前允许的能力生成结构化草案，不执行工具。
- PlanValidator：检查计划与版本；确认后版本不可原地修改。
- TaskOrchestrator：选步骤、推进状态、处理取消/暂停/恢复、维护任务截止时间。
- StepExecutor：执行单个步骤；调用 Deep Agents 时仍限制工具和内部循环。
- RetryController：集中分类异常、计算等待和调用次数；SDK 与图层不叠加隐藏重试。
- ToolExecutor：继续作为统一权限与审计入口，增加逻辑调用标识及尝试记录。
- EventStore：保存有序进度事件，SSE 只负责传输，不承担调度和业务状态。

步骤结束必须满足其输出契约：工具步骤要求成功审计和合法结果；分析/汇总步骤要求合法输出及所引用的真实上游结果。模型的文字“已经完成”不构成执行成功。语义质量另设评测，不能由简单非空字符串检查代替。

业务完成结果先在同一事务提交：step_attempt 终态、步骤产物、step 终态和事件。后续汇总使用已提交结果；成功工具不因为后续汇总失败而重新执行。

## 5. 数据模型与状态机

新增模型与现有问答 Run 分离，避免把每次聊天都变成任务：

|模型|职责与核心字段|
|---|---|
|Task|逻辑目标；owner_user_id、workspace_id、source_conversation_id、current_task_run_id|
|TaskRun|一次完整执行；confirmed_plan_revision、status、deadline_at、cancel_requested_at、lease_owner、lease_expires_at、fencing_token|
|PlanRevision|不可变计划版本；目标/上下文快照引用、步骤定义、确认人/时间、内容摘要|
|TaskStep|本轮步骤进度；step_key、depends_on、status、result_ref、当前尝试 ID|
|StepAttempt|步骤执行尝试；attempt_no、错误码、起止时间、结果引用|
|ActionInvocation|逻辑模型/工具调用账本；logical_action_id、步骤/计划版本、类型、参数摘要、受保护输入引用、幂等键、状态和最终结果引用|
|ActionAttempt|模型或工具请求的实际尝试；关联 ActionInvocation、attempt_no、错误类别、next_retry_at、耗时|
|TaskEvent|单调递增 sequence、事件类型、实体 ID、安全展示数据、时间|

TaskRun 状态：pending → planning → awaiting_confirmation → running → completed；执行中可进入 retry_wait、paused、failed、cancelled。步骤状态：pending、running、retry_wait、paused、succeeded、failed、cancelled、skipped。

- pending：依赖尚未就绪或等待领取。
- retry_wait：一个具体请求等待下次尝试，next_retry_at 必须持久化；其他已完成结果不变。
- paused：用户主动暂停，或外部请求结果不确定需要核对。暂停不表示成功。
- failed：永久错误、重试耗尽或超过截止时间；保留已完成产物。
- skipped：用户确认的新计划明确取消某步骤；不能把必要步骤跳过后自动标记任务完成。

Task 的展示状态从 current_task_run 推导，不再维护另一套可冲突的执行状态。不同步骤和尝试不能共享 AsyncSession。

## 6. 网络异常分类与重试范围

重试单位是“一次模型请求或一次工具请求”，不是整个 Task，也不是把整张 Agent 图从头运行。新尝试沿用同一个 logical_action_id，但有新的 attempt_no。

|情况|拟议策略|
|---|---|
|连接超时、临时连接重置、短暂 DNS 故障|在剩余时间与次数允许时重试|
|模型/只读 HTTP 工具收到 408、502、503、504|作为可重试候选；仍检查具体错误和接口语义|
|429 临时限流|按有效 Retry-After 等待，再尝试|
|额度不足、无余额、账户禁用等永久服务错误|即使 HTTP 状态相近，也不自动重试|
|401/403、工具未授权、参数校验失败|不重试，提示修正配置或权限|
|证书错误、地址配置错误、确定不存在的域名|不循环等待，直接报配置错误|
|数据库连接失败|停止推进；重连后对账，不能盲目重放不确定提交的事务|
|读取流中途断开|按下一节处理，不能把新回复追加到旧片段后|
|前端 SSE 断线|只重连订阅，不创建新任务、不重新调用模型|

异常分类要读取稳定的类型/状态/供应商错误码，不能靠完整错误文本猜测；日志不保存凭证或供应商敏感异常正文。未知错误默认不自动重试。

拟议首版默认值（尚未进入 .env）：

|配置|建议值|说明|
|---|---|---|
|单个模型请求最大尝试数|3|包含首次，最多重试 2 次|
|单个只读工具请求最大尝试数|3|工具必须声明可安全重放|
|退避基数 / 上限|2 秒 / 30 秒|无 Retry-After 时使用指数退避和随机抖动|
|连接超时|10 秒|和读取超时分开|
|模型读取空闲超时 / 单次硬超时|30 秒 / 120 秒|是否可由当前 SDK精确表达，实施前按锁定版本验证|
|计划生成总时限|300 秒|包括计划生成的网络重试与等待|
|已确认任务总时限|30 分钟|从开始执行计时，包含执行、等待及暂停；不会因重试重置|
|步骤数 / 重规划次数|8 / 2|重规划版本须重新确认|
|任务实际模型请求上限|30|含网络重试的真实请求数，防止多层循环失控|
|任务逻辑工具调用上限|20|每步骤仍有上限；网络尝试另计且受总时间限制|

第 n 次重试的无提示等待窗口为 min(30, 2 × 2^(n-1)) 秒，实际在窗口内随机取值。最多 3 次总尝试时，只有两段等待。UI 显示实际算出的时间，不承诺固定 2、4 秒。

Retry-After 同时支持秒数和 HTTP 日期：有效时不早于服务端要求重试；无效则使用退避。若建议等待超过允许自动等待窗口（建议 5 分钟），进入 paused 让用户选择；若已经超过任务剩余截止时间，则失败为 DEADLINE_EXCEEDED，不能截短等待后继续轰击服务。

重试、步骤循环、重规划共享任务总时限和调用计数。供应商 SDK 保持 max_retries=0；若使用图节点 RetryPolicy，则必须委托统一控制器，不能再与 SDK 重试相乘。

## 7. 等待、取消、权限与断线

进入等待前，在短事务内保存：operation、attempt_no、max_attempts、error_code、next_retry_at、deadline_at、版本/取消状态，并提交 retry_scheduled 事件。数据库事务结束后才能等待。

本地调度器可用定时唤醒扫描到期记录，或用可取消的异步等待作加速；数据库中的 next_retry_at 才是事实来源。不能使用 time.sleep 阻塞事件循环，也不能持有数据库连接等待网络恢复。

等待期间：

- 点击停止，先提交 cancel_requested_at，再唤醒执行器，阻止下次请求。
- 暂停保留计划和结果；恢复前检查截止时间、当前角色/成员状态、计划版本和数据有效性。
- 当前空间成员被停用或账号被禁用，终止执行并停止发送结果；管理员不能借此读取别人任务。
- 前端断线/关闭页面不取消任务；重连只请求快照和事件。

取消具有提交边界：取消请求先于完成事务提交时，不能再发布为成功；已经提交完成的结果不回滚。正在飞行的网络请求会尝试关闭，但不能承诺供应商一定停止计算或不收费。

“立即重试”按钮只能提前结束本地退避，不得绕过有效 Retry-After、截止时间、次数上限或权限检查。

## 8. 部分回复中断与避免重复执行

### 模型输出

每次模型生成使用独立 generation_id。首版选择“替换失败尝试”，不做文本层面断点续写：

1. 首 token 前网络失败：重试当前模型请求。
2. 已输出部分正文后断线：将该 generation 标记 interrupted，保留为历史尝试。
3. 新尝试生成新的全文快照，前端根据 generation_id 替换当前正文；不拼接两段独立生成的文本。
4. 部分 JSON/tool_call 参数不能执行，必须等完整模型响应通过校验。
5. 只重试当前模型节点；之前已成功的工具消息从持久化结果重建，不再次执行。

模型重试不保证相同答案，服务端只能保证展示与尝试归属清楚。若运行阶段尚不能重建准确的工具消息上下文，流中断后先标记失败，不能退回“重跑整个图”的捷径。

### 工具与外部副作用

工具对应的 ActionInvocation 需要稳定 logical_action_id，绑定计划版本、步骤、调用序号、规范化参数摘要与可信身份；实际每次请求单独记录 ActionAttempt。相同逻辑调用的网络重试复用标识。

- 只读工具：可在声明允许重放后重试；结果可能随时间变化，以最终提交的查询结果为准。
- 已完成工具：从执行账本复用已验证结果，不重做；需要新数据时显式新建逻辑调用。
- 未来写入工具：只有目标系统支持幂等键或能查询执行结果时，才可安全自动重试。
- “对方可能已写入，但响应丢失”：进入 paused/OUTCOME_UNKNOWN，先对账或人工核对，不能直接重写。

仅在本地建唯一索引不能保证外部系统 exactly-once。首版依旧只开放只读工具，审批与写入按后续阶段另行实现。

## 9. 重启恢复与检查点

新任务调度器在应用生命周期启动时扫描待处理任务，不依赖用户发起首次问答才恢复。领取任务使用行锁、租约和递增 fencing_token；所有推进提交都比较当前 token，防止过期执行器覆盖新执行器结果。

- 已完成步骤：校验上下文/计划/数据有效性后复用。
- retry_wait：按 next_retry_at 恢复；到期后先重验权限和截止时间。
- running 且租约失效：检查具体 ActionAttempt。安全只读请求可创建新尝试，不把状态直接改成成功。
- 不确定外部写入：暂停核对，不自动重放。
- paused/awaiting_confirmation：不擅自继续。

实施分两层：第一版恢复到业务步骤边界，失败的只读步骤可安全重建；之后引入 LangGraph PostgreSQL checkpointer，恢复步骤内部状态。二者均使用已有 PostgreSQL 数据库，不新建实例或第二套数据库，可用独立 schema/表前缀隔离检查点。

TaskRun/执行账本是业务状态权威，检查点是运行状态。共享 PostgreSQL 不代表两个独立连接的事务自动原子；必须用稳定操作 ID 和结果账本处理“工具已完成、检查点未写入”的窗口。恢复节点先对账再调用工具。

官方文档说明，检查点之后的节点在 replay 时可能重新执行 LLM/API 请求，不能把“有检查点”当作“不重复外部操作”的保证。参考：[持久化与回放](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[容错机制](https://docs.langchain.com/oss/python/langgraph/fault-tolerance)。具体 SDK 接口须按本项目锁定版本验证，本设计不直接照搬最新文档示例。

## 10. 前端与 API 草案

任务页面左侧展示版本化计划步骤，右侧展示当前步骤结果、真实工具依据与重试记录；保留普通问答入口。

等待提示示例：“模型服务暂时不可用，将于 3 秒后重试；已尝试 1/3 次。”提供停止、暂停、查看原因；次数耗尽后显示“本次执行失败，已完成 2/3 步”，允许明确发起新的执行尝试。

SSE 事件：plan_created、plan_confirmed、step_started、action_retry_scheduled、action_attempt_started、generation_replaced、step_succeeded、step_failed、task_paused、task_completed、task_cancelled。事件持久化，使用单调 sequence 重连，快照带当前 generation_id 和最后事件游标；重复/过期事件可忽略。不要把私有模型思维链当作进度展示。

拟议接口：

|接口|职责|
|---|---|
|POST /api/tasks|显式创建任务与规划尝试，需幂等键|
|GET /api/tasks/{id}|本人当前空间的权威快照|
|POST /api/tasks/{id}/confirm|确认精确 plan_revision 和摘要|
|POST /api/tasks/{id}/pause、resume、cancel|控制执行，幂等并带版本校验|
|POST /api/tasks/{id}/retry|失败后创建新的 TaskRun，引用旧尝试，不清空历史|
|GET /api/tasks/{id}/events|有权限的事件订阅与重连|

继续使用 Cookie、Origin、CSRF、X-Workspace-ID，用户身份由后端绑定。手动重试明确新建 TaskRun；正常网络重试则留在原 TaskRun 内增加 ActionAttempt。新执行中可引用旧的成功步骤产物，但须重验有效性并记录 source_attempt_id，不复制为“刚刚重新执行成功”。

## 11. 分步实施与验收

|步骤|交付|验收重点|
|---|---|---|
|P1|任务/计划/步骤/尝试模型及状态机|普通问答不自动建任务、版本与归属约束、取消竞态|
|P2|串行计划执行与进度页面|依赖、真实完成条件、失败保留、用户确认|
|P3|集中网络重试与等待展示|错误分类、Retry-After、时限、取消、无重复片段|
|P4|本地调度、租约与恢复|进程杀停、等待恢复、token 防旧提交、权限重验|
|P5|步骤内部检查点与受控重规划|工具执行与检查点之间崩溃、恢复对账、版本失效|
|P6|之后按需并行与独立 Worker|每任务独立会话、依赖汇总、并发上限与失败策略|

必须覆盖的故障注入：首 token 前断网、流式半途断网、503 后恢复、429 带秒数/日期/超长 Retry-After、401/额度不足不重试、等待时取消/撤权、到期与取消同时发生、工具成功后汇总失败、数据库提交确认丢失、任务重启、旧执行器迟到提交、外部写入结果不确定、SSE 重连不产生新模型请求。

重试测试使用可控时钟和随机数种子，不真实等待数分钟；网络使用受控 HTTP/故障代理，数据库恢复用专用测试库。真实模型另行验收，不把测试替身当作真实服务成功。首版串行通过之后再实现并行。

## 12. 当前决策与待实施事项

建议先实现 P1–P3，形成“确认计划 → 串行执行 → 网络等待/失败/取消”的闭环，再做 P4–P5 的崩溃恢复。P1–P3 期间要明确：页面刷新可恢复查询，不代表服务重启能自动续跑。

MCP 不作为本设计依赖；知识库可作为后续新 Tool 接入。当前阶段路线图不会因为本设计而被标记完成，实际实施顺序须在进入编码时更新。
