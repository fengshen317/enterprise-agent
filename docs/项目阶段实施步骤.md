# 企业 Agent 工作台：项目阶段实施步骤

创建日期：2026-11-03。

更新说明：阶段一已在现有 PostgreSQL 服务使用 postgres 用户完成建库、表结构初始化和完整本地验收，不依赖 Docker。证据见 [阶段一最终验收记录](development/阶段一最终验收记录.md)。

本文是当前项目正式开发的阶段实施路线图，依据已确认的产品方案与开发讨论整理。产品功能与交互范围见 [产品功能与原型说明](产品功能与原型说明.md)。

## 一、项目目标与执行原则

项目同时服务于企业级 Agent 开发学习和个人工程能力训练：完成一个可运行、可测试、可本地运行、可测试、可维护的产品，并能说明技术取舍、定位故障、验证权限边界。

- 按“设计 → 编码 → 测试 → 部署验证 → 更新技术文档 → 复盘”完成每个阶段。
- 每阶段交付一个可运行版本、一组验收证据和与实现一致的技术文档。
- 代码开发时同步补全相关技术文档；此约定仅适用于 `D:/project/enterprise-agent`。
- 现有 `prototype/` 保留为产品评审原型；正式前后端分别开发，原型演示能力不代表后端已经实现。
- 问答是统一工作入口：简单问题直接回答，复杂目标按需规划、调用工具并委派子 Agent；只读执行无需额外创建任务或确认计划。业务写入审批仍属于阶段六。
- 取消预算填写；任务创建、确认与 Agent 配置不引入预算输入。
- 优先完成完整业务链路，再按阶段引入队列、知识库、权限和审批等能力。
- 开发期需要明确标识尚未提供认证保护的环境；第三阶段权限验收前，仅在受控开发环境使用模拟或非敏感数据。

## 四、阶段一：工程初始化

### 目标

建立可持续开发的正式工程基础，使后续功能都有一致的配置、测试与启动方式。

### 实施步骤

1. 阅读当前原型与产品说明，确认目录职责和首版边界。
2. 保留 `prototype/`，建立 `frontend/`、`backend/` 和 `deploy/`。
3. 初始化 Vue 3、TypeScript、Vite 和 FastAPI 项目，配置依赖管理及锁文件。
4. 复用已有 PostgreSQL 服务，使用 postgres 用户，在同一实例内配置开发库和测试库；不新建实例，不引入 Docker。
5. 配置 Alembic，建立可重复执行的迁移流程。
6. 实现配置加载、健康检查、结构化日志、统一错误响应和自定义异常。
7. 配置后端 Ruff、mypy、pytest，前端类型检查及必要的基础测试。
8. 建立项目根目录 `AGENTS.md`，记录项目规范和技术文档同步要求。
9. 编写启动指南，按文档验证前后端启动、数据库连接、迁移和检查命令。

### 验收标准

- 按 README 可从空环境启动前后端与数据库。
- 健康检查正常，数据库不可用时有明确反馈。
- 空库能够通过迁移初始化；连接和会话正常释放。
- 静态检查和基础测试通过，配置样例可用，密钥不进入 Git。

### 文档交付物

开发指南、目录职责、环境变量说明、技术选型决策、基础测试与启动验收记录。

## 五、阶段二：真实问答

### 目标

打通“创建对话 → 提交问题 → 模型生成 → 保存回复 → 查询历史”的完整链路，再补全流式输出和异常状态。

### 实施步骤

1. 设计 `Conversation`、`Message`、`Run` 数据模型和迁移。
2. 明确三者职责：对话是交流容器，消息是内容记录，运行是一次生成或执行尝试。
3. 定义创建对话、会话列表、消息历史、创建运行、SSE 事件和取消运行的接口契约。
4. 先使用固定回复验证接口与持久化，再通过统一运行适配层接入 Deep Agents SDK 和一个真实模型。
5. 实现 SSE 流式回复、同一对话连续追问和历史查询。
6. 区分生成中、完成、失败和取消状态，明确部分回复的保存规则。
7. 将正式 Vue 页面接入后端，替换原型本地数据方式。
8. 测试使用模拟模型，真实模型调用作为独立的集成验证。

### 验收标准

- 连续追问可以引用当前对话上下文，刷新后能恢复已保存记录。
- 模型超时、调用失败和停止生成均有明确状态。
- 流式片段汇总为回复，不将每个字符分别建成一条消息。
- 日志能通过 `run_id` 关联执行过程，日常测试不依赖真实模型或费用。
- 普通问答不会创建业务任务；断线与服务重启后的运行状态有明确处理方式。

### 文档交付物

数据模型、问答时序、API 契约、SSE 事件格式、异常与取消处理说明、测试验收记录。

## 六、阶段三：身份与数据隔离

### 目标

建立可验证的访问边界，将阶段二的开发环境能力转为具有用户与工作空间隔离的应用能力。

### 实施步骤

1. 实现登录与退出，复用成熟的密码哈希和令牌组件。
2. 建立用户、工作空间、成员与基础角色模型。
3. 将对话、消息、运行记录关联到工作空间和用户；补全已有开发数据的迁移策略。
4. 为查询、修改、取消、SSE 订阅与下载入口实现服务端资源鉴权。
5. 明确身份与授权上下文由可信后台绑定，不能依赖模型传入的身份参数。
6. 编写跨用户和跨工作空间的越权测试。

### 验收标准

- 修改请求中的资源 ID，不能访问其他用户或工作空间的资源。
- 列表和详情采用一致的授权规则。
- 退出或失效的认证有明确处理，不泄露敏感内容。

### 文档交付物

身份与会话方案、权限矩阵、身份传递方式、资源归属与隔离规则、越权测试记录。

## 七、阶段四：工具与知识库

### 目标

让 Agent 在权限边界内调用真实能力、检索企业资料，并提供可追溯的回答依据。

### 实施步骤

1. 先实现一个只读原生 Tool，例如查询模拟销售系统。
2. 编写一个 MCP 服务，暴露同类业务能力，验证原生 Tool 与 MCP 的接入边界。
3. 统一工具标识、参数校验、身份传递、超时、错误和调用审计。
4. 建立文档上传、解析、分块、索引与检索流程。
5. 使用 PostgreSQL 与 pgvector 保存检索数据，执行资源权限过滤。
6. 为回答提供来源关联，处理资料不足时的反馈。
7. 明确文档状态，处理解析失败、重复上传、重新索引和删除后的索引清理。
8. 建立一组固定检索问题和预期来源，记录检索与回答效果。

### 验收标准

- 能追溯一次回答使用了哪些资料和工具结果。
- 无权限文档不会进入模型上下文，来源下载同样校验权限。
- 工具失败和文档处理失败不会被显示为成功。
- 原生 Tool 与 MCP 的同类操作遵循一致授权规则。

### 文档交付物

工具契约、MCP 接入说明、文档处理流程、检索与权限设计、失败处理策略、评测样例和结果。

当前 4.1 已交付原生只读工具、权限绑定、审计和问答展示；知识库 MVP 已接入 RAGFlow 1.0，支持空间/私有知识库、文档上传解析、主/子 Agent 检索和来源引用。详见 [阶段四实施计划](development/阶段四实施计划.md)、[工具架构与接口](development/原生工具与调用审计.md)、[阶段四验收记录](development/阶段四验收记录.md)、[知识库实现与验收](development/知识库实现与验收.md)。2026-11-12 进一步交付 Agent 工作台第一期：Agent 配置、工具目录、Markdown/SOP 技能、运行快照与写操作逐次审批（迁移 0012/0013），详见 [Agent 工作台实现与验收](development/Agent工作台实现与验收.md)。MCP 暂缓；HTTP/OpenAPI 外部工具、文档级 ACL、检索评测和索引版本仍待实施。

## 八、阶段五：后台任务与并行执行

### 目标

将对话扩展为持续执行的工作，建立不依赖浏览器连接的后台生命周期。

### 实施步骤

1. 本地阶段以问答 Run 为统一入口，主 Agent 按需规划、调用只读工具、委派受控子 Agent；后台执行不依赖浏览器订阅，需要独立 Worker 时再引入队列。
2. 计划与执行记录直接关联问答 Run，在消息内展示状态；不要求用户跳转页面创建任务或编辑 JSON。
3. 分别建立任务、执行尝试和 Agent 检查点，明确各自状态与关联关系。
4. 队列消息只承担分发职责，业务执行状态保存在数据库。
5. 接入 Deep Agents 规划与子 Agent，执行多个独立分析分支并汇总。
6. 保存检查点，展示阶段进度，生成可预览和下载的交付物。
7. 实现失败处理、受控重试、协作式取消与 Worker 故障后的恢复或失败收敛。
8. 处理数据库提交与队列分发不一致问题，验证幂等创建及必要的事务发件箱机制。

### 验收标准

- 关闭页面后任务继续运行，重新打开能查询持久化进度。
- 并行分支失败可定位到具体步骤，不共用不安全的数据库会话。
- 重复提交和重复投递不会重复创建逻辑任务。
- Worker 中断后不会永久停留在无解释的执行中状态。
- 取消和重试保留执行记录，任务权限不因子 Agent 委派而扩大。

### 文档交付物

任务与运行状态机、队列协议、并发策略、异步运行边界、取消语义、恢复与重试流程、交付物存储设计。

## 九、阶段六：人工审批

### 目标

以“修改客户跟进建议”为首个业务写入场景，完成受控授权、持久化暂停、恢复执行与审计闭环。

### 实施步骤

1. 在写入前创建明确的操作快照，保存目标资源、参数、版本与修改前后内容。
2. 暂停 Agent，保存检查点与独立审批记录。
3. 由审批人批准或拒绝，记录意见；拒绝原因必填。
4. 将审批结果绑定本次操作内容，参数变化后重新审批。
5. 恢复时校验当前权限、资源版本和审批有效性。
6. 使用幂等键避免重复写入，区分审批结果与实际业务执行结果。
7. 测试并发审批、重复请求、撤权、写入后响应丢失等情况。

### 验收标准

- 重复批准不会重复执行，同一审批的并发决策有确定结果。
- 参数改变必须重新审批，不能复用旧批准结果。
- 审批期间撤销权限，恢复执行时拒绝业务写入。
- 业务执行失败、部分成功和审批通过分别记录，可追溯到操作参数及执行尝试。

### 文档交付物

审批状态机、操作快照、并发控制、幂等与恢复设计、权限重验规则、审计字段及异常验收记录。

2026-11-12 已交付最小闭环：只读工具自动执行，`create_scheduled_task` 写工具逐次审批，`approvals`/`approval_events` 保存审批链，Run owner 决策，超时/取消/重启收敛。多级审批、管理员代审批、跨进程恢复和业务执行幂等仍待完善。

## 十、阶段七：工程加固与部署

### 目标

完成可重复运行、可定位故障、可验证质量、可恢复数据的交付能力。

### 实施步骤

1. 完善 CI：静态检查、测试、构建、迁移验证，失败阻止交付。
2. 用 `request_id`、`run_id` 关联日志，补全工具调用与模型调用的观测信息。
3. 完善敏感信息脱敏、配置和密钥管理。
4. 完成本地前端、API、Worker、数据库及相关服务的可重复启动与健康检查；未来需要服务器部署时另行确定环境。
5. 实施数据库与交付物备份，执行恢复演练。
6. 验证应用发布、回滚和数据库迁移兼容策略；不将有损数据库降级当作默认回滚手段。
7. 使用固定问答、检索和工具调用评测集验证模型或提示词变更。
8. 先定义并发与响应目标，再进行压测，记录瓶颈和改进。
9. 整理排障步骤、已知限制和阶段复盘。

### 验收标准

- 新环境可以依照文档部署，CI 结果与交付版本一致。
- 能通过日志定位一次失败并说明原因。
- 完成一次应用版本回滚和一次数据恢复演练，保留证据。
- 评测与压测有明确输入、环境、结果和限制，不只记录“通过”。
